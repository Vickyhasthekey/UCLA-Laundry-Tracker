# Member C: AWS deployment and integration

## Scope and current boundary

Member C owns `infra/`. The default runtime and web page under `infra/demo/` are
explicitly labeled integration fixtures, not A's React frontend or B's reporting
and status implementation. This allows deployment before teammates finish.
Do not use legacy root `backend/app.py`, `frontend/`, or `scripts/prepare.py` to
deploy this stack. Those are older local scaffolds with a different API contract.

Regional resources must stay in the selected Region, `us-east-2`. Confirm it in
AWS Settings > View all projects > Overview > Additional Info > Region.
Use profile `laundry-dev`. Deployment creates usage charges/consumes free credits;
check plan and spend status in AWS Settings > Billing. A Free plan is not a
promise of unlimited free usage.

## Prerequisites

AWS CLI v2, SAM CLI, uv, and Python 3.13. Install SAM using `uv tool install aws-sam-cli`.
Sign in if needed, without copying keys into any files:

```sh
aws login --profile laundry-dev --region us-east-2
aws sts get-caller-identity --profile laundry-dev
```

## Repeatable deployment

From the repository root:

```sh
uv run --with boto3 --with 'botocore[crt]' infra/deploy.py
```

The script validates SAM, builds the demo Lambda, deploys `laundry-dev`, updates
CORS to the generated HTTPS website origin, seeds two demo machines, stages a
frontend with its API URL, syncs to S3, and invalidates CloudFront. Re-running
updates the same stack and inventory records, without erasing reports. Outputs
are written to ignored `infra/deployment-state.json`; secret contents are never
printed, downloaded, or put in frontend configuration.

Initial CloudFront provisioning can take several minutes. The script does not
wait for edge invalidation completion; browser checks should wait for deployment.

## Infrastructure and data contract for B

| Resource | Key/index contract |
| --- | --- |
| Rooms | partition `roomId` |
| Machines | partition `roomId`, sort `machineId`; GSI `ByCode`: partition `code` |
| Reports | partition `machineId`, sort `reportKey` (`UTC timestamp#UUID`) |
| Report lookup | GSI `ByReportId`: partition `reportId`, for undo lookup |
| Device history | GSI `ByDeviceTime`: partition `deviceHash`, sort `reportKey` |
| RateLimits | partition `bucketKey`; numeric epoch-seconds `expiresAt` TTL |

GSI reads are eventually consistent. Use primary-key consistent reads where
immediate visibility matters. A GSI does not enforce uniqueness of machine codes;
B's seed/write path must ensure it. For undo, query ByReportId, then conditionally
update the base record owned by the same device. Never return deviceHash publicly.
Table keys are a proposed handoff; B's final `docs/api.md` must agree before switching.
Do not change deployed primary keys in place; retain and migrate data if needed.

Lambda receives `ROOMS_TABLE`, `MACHINES_TABLE`, `REPORTS_TABLE`, `RATE_LIMIT_TABLE`,
and `DEVICE_HASH_SECRET_ARN`. It retrieves the secret at runtime with its role.
The secret value is generated by Secrets Manager, never checked into Git or
passed as a plaintext Lambda environment value. Cache it only within a warm runtime.
Coordinate rotation: changing the key changes device identities and rate buckets.

The demo enforces 1 report/device/machine per rolling 180 seconds, 30/device/UTC
day and 300/IP/UTC day. Counters, cooldown, and report write use one transaction.
TTL removes old records asynchronously; conditions, not deletion timing, enforce
limits. HMAC-SHA256 hashes are domain-separated for device vs IP. Only hashes are
stored. `X-Device-Id` must be UUID; client-supplied IDs can be reset, so this is
abuse friction rather than authenticated identity. API Gateway sourceIp is used,
not X-Forwarded-For from the caller. Logs omit request bodies, device IDs and IPs.

The demo API provides `/health`, `/rooms`, `/rooms/{roomId}/machines`, and
GET/POST `/machines/{machineId}/reports`. POST accepts a fixed `issueType` and
optional empty `website` honeypot; no free text. Full `/machines/{code}` status,
DELETE `/reports/{id}` undo, outcome/setting dictionaries and status computation
are B-owned and are not implemented by this fixture.

## Switch to teammates' implementations

1. Obtain B's agreed API/schema and A's React code. Keep changes on a branch.
2. Replace Backend `CodeUri`, Runtime and Handler in `infra/template.yaml` with
   B's actual package. Add the agreed machine-detail and DELETE routes. Scope IAM
   to the handlers' operations; do not grant table scans to bypass a missing index.
3. If B uses TypeScript, configure SAM esbuild metadata and build dependencies.
   The current Python runtime is an isolated fixture, not a language requirement.
4. In A's frontend folder, install locked dependencies and build with
   `VITE_API_BASE_URL` set to the stack's ApiUrl. Ensure X-Device-Id is sent.
5. Publish A's build rather than the demo:

```sh
uv run --with boto3 --with 'botocore[crt]' infra/deploy.py --frontend-dir frontend/dist
```

For a frontend-only publish after a backend deployment:

```sh
uv run --with boto3 --with 'botocore[crt]' infra/deploy.py --publish-only --frontend-dir frontend/dist
```

CORS allows only the selected website origin plus content-type/X-Device-Id and
GET/POST/DELETE/OPTIONS. To test localhost, deploy AllowedOrigin=http://localhost:5173
temporarily, then restore the hosted origin. CORS is not authentication.

## Verification

- SAM lint: `sam validate --lint -t infra/template.yaml --region us-east-2 --profile laundry-dev`.
- Local tests: `uv run --with boto3 --with 'botocore[crt]' --with 'moto[dynamodb,secretsmanager]' python -m unittest discover -s infra/tests -v`.
- Live checks: `uv run --with certifi python infra/verify.py` (writes one demo report; do not point at production).
- Guard checks: `cfn-guard validate --rules infra/security.guard --data infra/template.yaml --output-format json`.
- `/health` responds 200; `/rooms` and machine list contain demo inventory.
- Browser: load HTTPS page on mobile, submit a button-only issue, reload and
  verify it persists. Repeat immediately and expect 429 with useful feedback.
- Bad issue/missing device UUID/honeypot/free text should return 400; unknown
  machine returns 404. Hashes never appear in public responses.
- OPTIONS from the hosted origin with X-Device-Id passes; another origin is not
  granted permission. Raw S3 object access is denied; CloudFront is accessible.
- Inspect API access logs and Lambda logs (seven-day retention). No custom
  CloudTrail trail was present at setup; this is reduced auditability, not a
  claim that a durable application trail has been configured.

## Security and data retention

S3 is private, encrypted, versioned, TLS-only, and accessible through CloudFront
OAC. Tables and Secrets Manager encrypt at rest. IAM permits specific table
operations/indexes plus one secret. API throttles are 5 requests/sec, burst 10;
these are best-effort traffic controls, not a guaranteed cost ceiling.
Tables, bucket, and secret are retained on deletion/replacement to protect data.
The anonymous demo is not a production-ready anti-abuse or authentication system.

## Cleanup

Keep the dev stack for team integration unless the project owner chooses removal.
Deleting the stack stops API/hosting infrastructure but retains the four tables,
versioned S3 bucket and secret. These can continue to incur charges. First record
resource names; only after explicit approval delete retained resources and all S3
object versions. Never run blanket project-wide deletion commands.

```sh
sam delete --stack-name laundry-dev --region us-east-2 --profile laundry-dev
```
